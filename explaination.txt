how it is stealthy-

This is the million-dollar question. if  shellcode simply calls "loud" APIs like CreateRemoteThread or WriteProcessMemory, a modern AV/EDR will see that behavior and flag it, regardless of whether it's coming from a proxy DLL or a regular EXE.
However, DLL proxying provides several layers of stealth that make it much harder for the AV to decide if the behavior is actually malicious.

1. The "Trusted Process" Umbrella
When an AV monitors API calls, it looks at the Source Process.
• If a random malware.exe calls VirtualAllocEx, it’s a 99% chance of being blocked.

• If msdtc.exe (a legitimate Windows service) or Steam.exe calls memory functions, the AV is much more "forgiving."


By proxying, your code is running inside the memory space of the trusted program. The AV sees the trusted program doing the work, which lowers the "Suspicion Score."

2. Bypassing "Static" Analysis
Most AVs scan files on your hard drive before they even run.
◇ Regular Malware: Has suspicious imports (like WriteProcessMemory) in its header. The AV sees this and deletes the file immediately.

◇ Proxy DLL: Your proxy DLL mostly contains "boring" jumps to legitimate functions (like GetFileVersionInfo). It looks like a utility tool.

◇ Many attackers use Encoding or Encryption (like XOR) on their shellcode. The AV scans the DLL, sees random gibberish bytes, and doesn't find a "signature."



3. Bypassing "Behavioral" Analysis (The Hooking Battle)
This is where the real fight happens. Modern EDRs (Endpoint Detection and Response) "hook" the Windows APIs to watch them. To bypass this, proxy DLLs often use Indirect Techniques:
◇ Direct Syscalls: Instead of calling VirtualAlloc (which the AV is watching), the code inside your proxy DLL can talk directly to the Windows Kernel. This bypasses the AV's "hooks" entirely.

◇ Module Stomping: You use the memory space already allocated for a legitimate DLL to hide your shellcode.

◇ Wait and See: Since your code is running independently in the background, it can wait for 10 minutes, or wait until the user moves the mouse, before executing. This bypasses "Sandboxes" that only watch a program for 30 seconds.
